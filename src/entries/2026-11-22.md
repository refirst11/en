---
title: Not Hoisting the Lookup Tables
date: '2026-11/22'
---

When a style is chosen at runtime, Plumeria compiles it to a small table of class strings, written inline:

```js
({__proto__:null,"small":"xhrr6ses x1v10r0u","large":"xpdfgu2b xj7b4jff"}[size] || "")
```

The table is built again on every render, so I tried hoisting it to the top of the module so it would be built only once. The change was merged, and I reverted it before the release went out.

## It Needed a Function

A `const` at the top of the module breaks import cycles. A function declaration can be called before its module evaluates, and reading a `const` that early throws. So the hoisted table became a `var` with an initializer function:

```js
var t;
function n() { return (t = {__proto__:null,"small":"xhrr6ses x1v10r0u","large":"xpdfgu2b xj7b4jff"}); }
```

## The Bundler Decides

Turbopack inlined that function, so the built output was close to the original. A Vite 8 production build kept `function n(){…}` as it was, and the function ended up in the bundle.

Plumeria's case is that what ships is class names, CSS and a lookup. A helper function in the bundle contradicts that, and whether it shows up depends on the bundler.

The gain did not justify it either. An SSR render of 1,000 instances took 17.67 ms with inline tables and 17.64 ms with hoisted ones.

With Next.js, a page prerendered at build time is served from the cache, so neither version runs at all. The SSR numbers above bypassed that cache to render on every request.

The inline table has no name to collide with, and every bundler leaves it as written. After the build, a lookup costs the same no matter what input it gets, inline or not.
